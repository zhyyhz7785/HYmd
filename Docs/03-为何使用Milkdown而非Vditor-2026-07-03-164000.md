## 0. 结论先行

**HYmd 在 VS Code 扩展里选 Milkdown Crepe，不选 Vditor IR，不是因为 Vditor 差，而是因为产品边界不同。**

| 项目 | 编辑内核 | 场景 |
|---|---|---|
| **HyCADTool.MarkdownEditor** | Vditor 3.10.8 IR | AutoCAD 内嵌、Typora 风写作、已有双 WebView 经验 |
| **HYmd（hymd-vscode）** | Milkdown Crepe | IDE 内 CustomEditor、**文本真相源**、HyMD 扩展块 + Univer |

Vditor 在 MarkdownEditor 中已被验证为优秀的 IR 编辑器；HYmd **刻意不复用**同一内核，以便与 `remark` 解析栈、VS Code 文档模型、HyMD fenced 块协议对齐。**不是互斥，是分工。**

---

## 1. 问题从哪来

读者常见疑问：

1. 团队已在 `HyCADTool.MarkdownEditor` 深度集成 Vditor，为何 HYmd 另起 Milkdown？
2. Vditor IR 功能更全（KaTeX、上传、工具栏），Milkdown Crepe 是否「降级」？
3. 未来能否统一成 Vditor？

本文回答 **HYmd 宿主为 VS Code 扩展时** 的正文编辑器选型逻辑；不涉及 CAD 图纸 Flow（那是 MarkdownEditor 自研 Preview 的职责，见 Doc/056）。

---

## 2. HyMD 对正文编辑器的硬性要求

来自 [hymd-spec v0.1](../spec/hymd-spec-v0.1.md) 与 M0/M1 实现：

| 要求 | 含义 | 对内核的约束 |
|---|---|---|
| **文本真相源** | 磁盘上的 `.hy.md` 是唯一持久化格式 | 编辑结果必须稳定输出 CommonMark/GFM 字符串 |
| **扩展块 = fenced code** | `sheet`/`slide`/`layout` 等以围栏代码块存在 | 内核不能把块「吃」进富文本 DOM 后无法还原 |
| **优雅降级** | 任意 MD 工具打开仍见可读 code fence | 块语法不能被 WYSIWYG 静默改写 |
| **可拔插引擎** | 表格/公式走 Univer snapshot，不走 prose 逆转换 | 正文编辑器只负责 prose，不负责重表格 |
| **与 `@hymd/parser` 同栈** | parse → serialize 往返测试 | 最好共用 remark/unified 语义 |

这些要求优先于「开箱功能多不多」。

## 3. 选 Milkdown 的六个理由

### 3.1 与 HyMD 解析栈同生态（remark / unified）

```
.hy.md 文件
    ↓ @hymd/parser (remark)
AST + 扩展块识别
    ↓
Milkdown Crepe（ProseMirror，md 优先）
    ↓ markdownUpdated
整文档 Markdown 字符串 → VS Code TextDocument
```

- **Milkdown** 建立在 ProseMirror + unified/remark 思路上，与 `packages/hymd-parser` 的 **同一套 Markdown 语义世界** 更容易对齐。
- **Vditor** 自带 **Lute** 解析器（Go→JS），与 remark 是**第二套 AST 规则**。双解析器意味着：
  - fenced 块 info string（如 `` ```sheet id=load-table ``）在两边的 round-trip 行为可能不一致；
  - 单元测试要维护 Lute 与 remark 两套 golden case。

产品调研 [001](../Doc/001-md风格增强文档套件-产品调研-2026-07-03-102959.md) 已把格式层定为 `unified/remark`，Prose 层默认 **Milkdown（md 优先）**，Vditor 列为「已有经验」备选——HYmd M0 落地时选了与格式层默认一致的一侧。

### 3.2 VS Code CustomTextEditor 集成模型

HYmd 的数据流（见 `editorProvider.ts` + `src-webview/index.ts`）：

1. Host 读 `TextDocument.getText()` → `init` 消息进 webview  
2. Crepe `markdownUpdated` → 220ms debounce → `edit` 消息  
3. Host `WorkspaceEdit` **整文档 replace** 写回磁盘  
4. 外部变更 → `externalUpdate` + 版本号 → Crepe `replaceAll(content)`

Milkdown Crepe 为此类集成提供了清晰钩子：

```typescript
// packages/hymd-vscode/src-webview/index.ts（节选）
crepe.on((api) => {
  api.markdownUpdated((_ctx, markdown, prevMarkdown) => {
    if (markdown === prevMarkdown) return;
    sync.onLocalEdit(markdown);
    requestAnimationFrame(() => decorateHymdBlocks(...));
  });
});
await crepe.editor.action(replaceAll(content)); // 外部同步
```

**Vditor IR** 在 MarkdownEditor 中的集成方式是：

- C# 生成 HTML 模板，`input` 回调 `postMessage`；
- `getValue()` / `setValue()` 经 WebView2 脚本桥；
- 快捷键需与 WPF **PreviewKeyDown** 协同，并拦截 Vditor 内置冲突键（见 `VditorHtmlTemplate.cs`）。

在 **VS Code** 里：

- 快捷键归 **Command Palette / 默认键位** 管，Vditor 内置 toolbar 快捷键易与 `Ctrl+K`、`Ctrl+Shift+P` 等冲突；
- 主题应跟 `vscode.window.activeColorTheme`，Vditor 自带 classic/dark 主题体系需额外桥接；
- 通信是 `acquireVsCodeApi().postMessage`，不是 `window.chrome.webview`——Vditor 模板要整页重写，无法直接搬 MarkdownEditor 的 `VditorHtmlTemplate.cs`。

Milkdown 作为 **可嵌入组件**（`root: '#editor-root'`），比 **整页 Vditor 应用** 更贴合 CustomEditor 的「Host 管文档、Webview 管视图」分工。

### 3.3 HyMD 扩展块依赖「DOM 装饰」模式

M1 `sheet` 块的实现路径：

1. Milkdown 把 `` ```sheet ... ``` `` 渲染为普通 `<pre><code class="language-sheet ...">`  
2. `decorateHymdBlocks()` 扫描 DOM，挂 badge、Univer 预览、编辑按钮  
3. 块内重编辑走 **snapshot JSON**，不经过 prose 的 HTML 逆转换  

```typescript
// blockCards.ts：在 code fence DOM 上叠加 HyMD UI
root.querySelectorAll('pre code').forEach((codeEl) => {
  const lang = langClass.replace('language-', '');
  if (!isHymdBlockLang(lang)) return;
  pre.classList.add('hymd-block-card');
  // sheet → registerSheetPreview / openSheetOverlay
});
```

这要求：

- 扩展块在编辑器 DOM 里 **仍以 code fence 形态存在**；
- 每次 `markdownUpdated` 后可 **幂等** 重跑装饰（Univer 预览重挂）。

ProseMirror（Milkdown 底座）对 **code block 节点** 的控制是插件级的，适合「保留 fence + 外挂 UI」。  
Vditor IR 会把 Markdown **转成 IR 混合视图**，对自定义 fenced 语言块的行为 less predictable——存在被折叠、重排或 WYSIWYG 语义污染的风险，与 HyMD「块 = 可读 fence」冲突。

### 3.4 职责分离：Vditor 擅长的不是 HyMD 的正文边界

Doc/056 对 MarkdownEditor 的结论同样适用于 HyMD：

| 能力 | 谁做 |
|---|---|
| Typora 风 prose WYSIWYG、工具栏、KaTeX | Vditor / Milkdown 均可 |
| 重表格 + 公式 + 合并单元格 | **Univer**（`hymd-blocks-sheet`） |
| 分栏分页 / mm 纸张 | **layout 引擎**（未来 `hymd-layout`，移植 Preview Flow） |
| md 幻灯 | **Marp**（未来 `slide` 块） |

HYmd 刻意 **不在正文编辑器里堆 Vditor 的表格/公式能力**，因为：

- 表格公式已在 Univer 块里做得更好；
- 若在 Milkdown/Vditor 里再做一套，会与 sheet 块 **双轨维护**。

因此「Vditor 功能比 Crepe 多」在 HYmd 里 **权重下降**——多出来的部分本就不该由 prose 编辑器承担。

### 3.5 构建与仓库边界

| 维度 | Milkdown（当前） | Vditor 3.10.8 |
|---|---|---|
| 语言栈 | 纯 TS，esbuild 打进 `webview.js` | TS/JS + Lute wasm/JS，体积大 |
| 与 extension 关系 | 与 Univer、`@hymd/parser` 同属 npm monorepo | 需另维护 HTML 模板、CDN/本地缓存（MarkdownEditor 的 `VditorCacheManager`） |
| 宿主 API | 不绑定 WebView2 | MarkdownEditor 已绑定 `chrome.webview.postMessage` |

HYmd 仓库定位是 **格式 + 引擎 + VS Code 扩展**，与 `hy-cad-tool` **解耦**。把 Vditor 搬进来意味着：

- 复制/维护一套 WPF 时代验证过的 HTML 模板与资源缓存；
- webview 包体积在已有 Univer ~22MB 之上再涨一截。

Milkdown Crepe 模块化引入，与现有 `esbuild.mjs` 单文件 bundle 流程一致。

### 3.6 产品分工：避免与 MarkdownEditor 重复投资

| 代码库 | 职责 |
|---|---|
| `hy-cad-tool/.../MarkdownEditor` | CAD 内嵌编辑 + 图纸 Flow，**继续 Vditor** |
| `HYmd` |  portable `.hy.md` 规范 + IDE 插件 + 块引擎 |

两套产品 **共享规范与 snapshot 格式**，不共享 UI 内核。MarkdownEditor 已是 Vditor 的「深度定制宿主」；HYmd 若再选 Vditor，会：

- 把 VS Code 场景硬套进 WebView2 模板思路；
- 模糊「CAD 专用 vs 通用 HyMD 文档」边界。

## 4. Vditor IR 的优势（为何不说是「降级」）

公平起见，Vditor 在以下方面 **强于当前 Milkdown Crepe 配置**：

| 维度 | Vditor IR | HYmd Milkdown Crepe（M1） |
|---|---|---|
| 开箱工具栏 | 20+ 命令，成熟 | Crepe 内置，可关闭部分 feature |
| 数学公式 | KaTeX 内置 | `latex: false`，公式走 Univer |
| 图片上传 | 拖拽 + base64 | 未做 |
| 代码高亮 | highlight.js 完整 | Crepe codeBlock 有，弱于 Vditor content-theme |
| 中文 IME | 久经 MarkdownEditor 验证 | 自研 composition 缓冲，仍在打磨 |
| 团队熟悉度 | 高（`VditorHtmlTemplate.cs`） | 新栈 |

若 HYmd 的目标是 **Standalone Typora 克隆**，Vditor 会是强候选。  
但 HyMD 目标是 **「标准 md + 可拔插块 + IDE 内编辑」**，上述 Vditor 优势大多被 **Univer / 未来 Marp / layout** 分流，而非 prose 编辑器独占。

## 5. 决策对照表

| 评估项 | Milkdown Crepe | Vditor 3.10.8 IR | HYmd 权重下的胜者 |
|---|---|---|---|
| 与 `@hymd/parser` 语义一致 | 高 | 中（Lute 第二套） | **Milkdown** |
| VS Code CustomEditor 嵌入 | 高（组件化） | 中（整页 widget） | **Milkdown** |
| HyMD fenced 块 + DOM 装饰 | 高 | 中–低 | **Milkdown** |
| 开箱 WYSIWYG 功能 richness | 中 | 高 | Vditor（但非首要） |
| CAD/WebView2 宿主 | 低 | 高（已验证） | 不适用 HYmd |
| npm/esbuild 单体扩展 | 高 | 中 | **Milkdown** |
| 与 MarkdownEditor 代码复用 | 低 | 高 | 刻意不复用 |

## 6. 何时仍会考虑 Vditor

以下场景 **不推翻** 本文结论，但可能引入 Vditor 作为 **第二 prose 引擎**（产品调研中的 `hymd-blocks-prose` 备选）：

| 场景 | 说明 |
|---|---|
| **WPF 宿主 `hymd-host`** | 复用 MarkdownEditor 壳 + Vditor，服务非 IDE 用户 |
| **Crepe 功能瓶颈** | 若 prose 侧必须要 KaTeX/上传而无意进 Univer |
| **remark/Lute 对齐成本过高** | 若实测 round-trip 差异可接受，可评估 Vditor 单栈 |

切换成本：需重写 webview 同步层、块装饰选择器、快捷键与主题桥接；**M1 阶段不划算**。

---

## 7. 已知代价与后续

| 代价 | 对策 |
|---|---|
| Crepe 功能少于 Vditor | 表格/公式走 sheet 块；必要时开 `latex` 或加 Milkdown 插件 |
| `decorateHymdBlocks` 与 ProseMirror 重渲染 | 幂等重挂 Univer；overlay 时暂停 sync |
| 整文档 replace 性能 | M2+ 增量 diff（与内核无关） |
| 代码块观感弱于 Vditor | 借鉴 MarkdownEditor 的 content-theme / highlight.js 配置 |

---

## 8. 一句话记忆

**MarkdownEditor 用 Vditor，是因为「在 CAD 里写得像 Typora」；HYmd 用 Milkdown，是因为「在 IDE 里守 md 文本 + fenced 块 + remark 同栈」。**

重能力不在 prose 编辑器里卷，而在 Univer / Marp / layout 块里做——这与 Doc/056「职责分离，非二选一」是同一原则在 HYmd 产品线上的落地。
