## 1. 我们在解决什么问题？（用生活语言）

想象你要写一份**结构计算书**：

- 大部分是普通文字、标题、列表（像 Word 里写说明）；
- 中间要插一张**能算数的表格**（像 Excel）；
- 以后可能还要**按 A4 纸排版、多栏、插幻灯片**。

传统做法：Word 一份、Excel 一份、PPT 一份，改来改去很乱。

**HYmd 的想法**：尽量用**一个文本文件**装下全部内容——像一本「带特殊标记的笔记本」。任何普通笔记本软件打开，至少还能**读到文字**；我们的专用软件打开，则把表格、幻灯等**变成好看、可编辑的界面**。

[03 号文档](03-为何使用Milkdown而非Vditor-2026-07-03-164000.md) 讨论的是：**写「普通文字那一段」时，该用哪一款「写字工具」**——选 Milkdown，不选 Vditor。下面先把文档里出现的词一个个讲清楚。

## 2. 概念地图（从外到内）

可以把整个系统想成 **一家餐厅**：

```
你（用户）
  ↓ 打开文件、打字
【门面 / 宿主】= 你坐进哪家店（VS Code 编辑器，或 AutoCAD 里的窗口）
  ↓
【编辑区 / Webview】= 店里的装修好的用餐区（网页界面，但不是浏览器）
  ↓
【写字引擎】= 厨师（Milkdown 或 Vditor：把字变成「所见即所得」）
  ↓
【保存格式】= 最后装进外卖盒的原文（.hy.md 纯文本文件）
  ↓
【特殊菜 / 扩展块】= 表格块用 Univer 做，不用普通写字引擎硬做
```

读 03 号文档时，只要记住：**03 讨论的是「厨师选 Milkdown 还是 Vditor」**，不是整张餐厅要不要开。

## 3. 术语词典（每个词：是什么 · 从哪来 · 在项目里指什么）

### 3.1 文件与写作格式

#### Markdown（读音：马克当）

| | |
|---|---|
| **是什么** | 一种「用简单符号写文档」的写法。例如 `# 标题`、`- 列表项`、`**粗体**`。 |
| **从哪来** | 2004 年前后由 John Gruber 提出，想让写博客的人**不用打开 Word** 也能排版。 |
| **在项目里** | HYmd 文档的正文默认就是 Markdown 语法。文件常叫 `某某.md` 或 `某某.hy.md`。 |

#### `.md` / `.hy.md`（文件扩展名）

| | |
|---|---|
| **是什么** | 文件名末尾的点加字母，告诉电脑「这是什么类型的文件」，像信封上的「信/账单」。 |
| **从哪来** | 操作系统早年就有的习惯。`.md` = Markdown 文件。 |
| **在项目里** | `.hy.md` = 「仍是 Markdown，但按 HyMD 规则可以带表格块等特殊段落」。用 `.md` 结尾是为了：**别的软件也认它是普通 Markdown**。 |

#### HyMD / HYmd

| | |
|---|---|
| **是什么** | 你们团队定义的「增强版 Markdown」格式名字（Hy = 你们品牌，MD = Markdown）。 |
| **从哪来** | 产品立项时起的名，见 [spec/hymd-spec-v0.1.md](../spec/hymd-spec-v0.1.md)。 |
| **在项目里** | **HYmd** 常指整个仓库/产品线；**HyMD** 常指文件格式规范。日常可当作一回事。 |

#### 文本真相源

| | |
|---|---|
| **是什么** | 最终以**磁盘上那份纯文字文件**为准；界面再漂亮，保存时必须能还原成同一套文字。 |
| **从哪来** | 软件术语 *source of truth*（唯一可靠来源），这里译成白话。 |
| **在项目里** | 你的 `报告.hy.md` 是「原件」；编辑器只是「看和改的窗口」。这样 Git、备份、别的软件都能读原件。 |

#### CommonMark / GFM

| | |
|---|---|
| **是什么** | 两本「Markdown 标准说明书」。GFM（GitHub Flavored Markdown）在标准上加了表格、任务列表等。 |
| **从哪来** | CommonMark 2014 年起整理 Markdown 歧义；GFM 来自 GitHub 网站。 |
| **在项目里** | HyMD 说：正文遵守这些标准，这样和外界工具兼容。 |

### 3.2 「看得见排版」的编辑方式

#### WYSIWYG（读音：Wizi-wig，What You See Is What You Get）

| | |
|---|---|
| **是什么** | 「所见即所得」——屏幕上看到粗体就是粗体，**不用**看到 `**粗体**` 这种符号。 |
| **从哪来** | 1980 年代 Word、PageMaker 时代就有的说法。 |
| **在项目里** | HYmd 打开 WYSIWYG 模式时，你像在 Typora 里写，而不是看满屏符号。 |

#### Typora

| | |
|---|---|
| **是什么** | 一款很有名的 Markdown **所见即所得**写作软件（要付费）。 |
| **从哪来** | 独立软件，不是你们写的。 |
| **在项目里** | 03 文档说 MarkdownEditor「写得像 Typora」= 追求那种流畅写作体验。 |

#### IR 模式（Vditor 专用词）

| | |
|---|---|
| **是什么** | Vditor 的一种编辑方式：**中间态渲染**——比纯符号少，比 Word 仍偏 Markdown 结构。 |
| **从哪来** | Vditor 作者起的名，IR = Instant Rendering（即时渲染）。 |
| **在项目里** | `HyCADTool.MarkdownEditor` 里左侧编辑区用的就是 Vditor IR。 |

#### prose / 正文

| | |
|---|---|
| **是什么** | 相对「表格块、幻灯块」而言的**普通段落文字**部分。 |
| **从哪来** | 英文 prose = 散文、正文。 |
| **在项目里** | 「prose 编辑器」= 只负责标题、段落、列表，不负责 Excel 级表格。 |

### 3.3 两款「写字引擎」（03 的核心）

#### Vditor

| | |
|---|---|
| **是什么** | 别人写好的一套 **网页 Markdown 编辑器**（开源，带工具栏、公式、上传图等）。版本 3.10.8 是你们用的号。 |
| **从哪来** | 中国开发者 B3log 社区的项目，GitHub 上可下载。 |
| **在项目里** | 用在 **AutoCAD 插件**里的 `MarkdownEditor`，**没有**用在 HYmd 的 VS Code 扩展里。 |

#### Milkdown

| | |
|---|---|
| **是什么** | 另一套 **网页 Markdown 编辑器框架**，强调「Markdown 优先、可拼装插件」。 |
| **从哪来** | 开源项目 [milkdown.dev](https://milkdown.dev)，底座是 ProseMirror（见下）。 |
| **在项目里** | HYmd 的 VS Code 扩展 `hymd-vscode` 用它做 WYSIWYG。 |

#### Crepe

| | |
|---|---|
| **是什么** | Milkdown 官方提供的「**开箱即用**」皮肤+工具栏套餐，不用自己拼插件。 |
| **从哪来** | Milkdown 团队 2024 年前后推出的高层封装。 |
| **在项目里** | 代码里 `new Crepe({...})` 就是启动编辑器。 |

#### 为什么有两个引擎？（Milkdown vs Vditor 一句话）

| | 比喻 | 结论 |
|---|---|---|
| Vditor | 功能齐全的**整机品牌机**，拿来就能用，但内部规则自家一套 | 适合 CAD 里「整页编辑器」 |
| Milkdown Crepe | **可拆装的组件**，和 HYmd 其它零件（解析器、VS Code）同一套螺丝 | 适合 HYmd「文件格式优先」 |

03 号文档的**全部理由**，本质就是上表第二列的展开。

### 3.4 软件放在哪运行（宿主）

#### 程序 / 软件 / 应用

| | |
|---|---|
| **是什么** | 电脑里运行的、帮你完成任务的指令集合。Word、微信、AutoCAD 都是。 |
| **在项目里** | HYmd 涉及多个程序协作（见下）。 |

#### AutoCAD / CAD

| | |
|---|---|
| **是什么** | 工程绘图软件，画施工图用。 |
| **在项目里** | `hy-cad-tool` 是给 AutoCAD 加的插件；其中的 **MarkdownEditor** 在 CAD 里弹出写说明书的窗口。 |

#### VS Code / IDE

| | |
|---|---|
| **是什么** | **VS Code** = 微软出的免费「写代码/写文档」编辑器，界面像加强版记事本。**IDE** = 集成开发环境，泛指这类工具（Cursor 基于 VS Code）。 |
| **从哪来** | VS Code 2015 年发布。 |
| **在项目里** | HYmd 以 **VS Code 扩展**形式提供 WYSIWYG；`hymd-code` 是你们改过的 VS Code 发行版（HYmd Code）。 |

#### 扩展（Extension / 插件）

| | |
|---|---|
| **是什么** | 给 VS Code **加装的功能包**，像给手机装 App。 |
| **在项目里** | `hymd-vscode` 扩展：打开 `.hy.md` 时显示 HyMD 所见即所得界面。 |

#### 宿主（Host）

| | |
|---|---|
| **是什么** | 「**容器程序**」——真正管文件、菜单、保存的是谁。扩展里的编辑界面是「住」在 VS Code 里的。 |
| **在项目里** | VS Code 主程序 = 宿主；扩展里的 TypeScript 代码 = 宿主侧逻辑。 |

#### CustomEditor / CustomTextEditor（自定义编辑器）

| | |
|---|---|
| **是什么** | VS Code 的一种机制：某种文件**不用默认文本框**，而用**自定义界面**打开（这里是 WYSIWYG 网页）。 |
| **从哪来** | VS Code API 设计。 |
| **在项目里** | 双击 `报告.hy.md` → 走 HyMD WYSIWYG，而不是纯字符界面。 |

#### WPF

| | |
|---|---|
| **是什么** | 微软的一套**做 Windows 窗口界面**的技术（按钮、面板那种）。 |
| **在项目里** | MarkdownEditor 的窗口是 WPF + 内嵌网页，不是 VS Code。 |

#### WebView2 / Webview

| | |
|---|---|
| **是什么** | 在**普通软件窗口里开一小块「网页」**的组件。外观像浏览器里的一页，但没有地址栏。 |
| **从哪来** | WebView2 基于微软 Edge 浏览器内核。 |
| **在项目里** | MarkdownEditor 用 **两个** WebView2（一个 Vditor，一个图纸预览）；HYmd 扩展用 **一个** Webview 装 Milkdown + Univer。 |

### 3.5 文件怎么被「读懂」（解析）

#### 解析 / parser（解析器）

| | |
|---|---|
| **是什么** | 把**人写的文字**按规则**拆开、理解**的程序，像老师批改作文前先认段落和标题。 |
| **在项目里** | `@hymd/parser` 包：读 `.hy.md`，认出哪里是标题、哪里是 `sheet` 表格块。 |

#### remark / unified

| | |
|---|---|
| **是什么** | JavaScript 世界里常用的 **Markdown 解析工具链**名字。unified 是流水线，remark 专门处理 Markdown。 |
| **从哪来** | 开源社区，GitHub 上大量项目在用。 |
| **在项目里** | `hymd-parser` 基于 remark，和 Milkdown **同一语言生态**，规则容易对齐。 |

#### Lute

| | |
|---|---|
| **是什么** | **Vditor 内置**的 Markdown 解析器，用 Go 语言写成再编译到网页里。 |
| **从哪来** | Vditor 团队。 |
| **在项目里** | 若 HYmd 也用 Vditor，就会存在 **Lute 和 remark 两套规则**，同一段话保存两次可能细节不一致——03 文档认为这是风险。 |

#### AST（抽象语法树）

| | |
|---|---|
| **是什么** | 解析后的**结构化提纲**：第 1 段是标题、第 2 段是列表……像目录树，不是给人看的，是给程序用的。 |
| **从哪来** | 编译原理通用概念。 |
| **在项目里** | parser 产出 AST，再决定哪里渲染成表格卡片。 |

#### parse / serialize（解析 / 序列化）

| | |
|---|---|
| **是什么** | **parse** = 文字 → 结构；**serialize** = 结构 → 文字。 |
| **在项目里** | 「往返测试」= 读入文件再写回，内容和原来一致。 |

#### round-trip（往返）

| | |
|---|---|
| **是什么** | 改完再存、再打开，**不丢格式、不乱码**。 |
| **在项目里** | HyMD 要求扩展块在保存后仍是可读的 `` ```sheet ... ``` `` 形式。 |

### 3.6 HyMD 特殊段落（扩展块）

#### fenced code / 围栏代码块

| | |
|---|---|
| **是什么** | Markdown 里用 **三反引号** 包起来的一段，本来用于贴「程序代码」。HyMD **借这个形状**装表格等。 |
| **例子** | `` ```sheet id=荷载表 `` 开头，`` ``` `` 结尾，中间是 YAML 或引用 JSON。 |
| **从哪来** | Markdown 标准语法；HyMD 扩展了「语言名」可以是 `sheet`。 |
| **在项目里** | 即使不用 HyMD 软件，用记事本打开也能看到这段「围栏」，**优雅降级**。 |

#### 扩展块 / sheet / slide / layout

| | |
|---|---|
| **是什么** | HyMD 定义的几种**特殊围栏**：`sheet`=表格，`slide`=幻灯，`layout`=排版，`calc`=计算（规划中）。 |
| **在项目里** | M1 已实现 **sheet**：围栏里写表格块，界面显示 Excel 式预览。 |

#### Univer

| | |
|---|---|
| **是什么** | 开源的**网页版表格/文档引擎**（类似在线 Excel 的内核）。 |
| **从哪来** | [univer.ai](https://univer.ai)，Apache 许可证。 |
| **在项目里** | `hymd-blocks-sheet` 包；表格**真正编辑**在 Univer 里做，不在 Milkdown 里硬做。 |

#### snapshot（快照）

| | |
|---|---|
| **是什么** | 某一时刻表格的**完整数据打包**（JSON 文件），像 Excel 另存为一份结构数据。 |
| **在项目里** | 存在 `.hy.assets/` 文件夹；围栏里只写「引用哪份快照」。 |

#### 优雅降级

| | |
|---|---|
| **是什么** | 没有 HyMD 软件时，用普通 Markdown 查看器打开，**至少还能读懂**（看到围栏和文字，而不是乱码）。 |
| **在项目里** | 设计原则，见 hymd-spec。 |

#### DOM / HTML

| | |
|---|---|
| **是什么** | 网页在屏幕上的**结构树**（哪是标题、哪是代码块）。HTML 是描述这种结构的标签语言。 |
| **在项目里** | Milkdown 把围栏画成网页上的 `<pre><code>`；再在它的「外面」贴按钮和表格预览，叫 **DOM 装饰**。 |

#### 逆转换

| | |
|---|---|
| **是什么** | 从**屏幕上改过的样子**再猜回**原始 Markdown 文字**。容易丢信息。 |
| **在项目里** | MarkdownEditor 的「图纸预览区」曾用逆转换，容易丢代码块标记；HyMD **避免**对表格做逆转换，改用 snapshot。 |

### 3.6 程序之间怎么说话

#### 消息 / postMessage

| | |
|---|---|
| **是什么** | 网页和外面宿主**互相传纸条**：「用户改字了」「请保存这段文字」。 |
| **在项目里** | webview 里 `vscode.postMessage({ type: 'edit', content: '...' })`。 |

#### debounce（防抖，220ms）

| | |
|---|---|
| **是什么** | 你连续打字时，**停笔约 0.22 秒**再通知保存，避免每个字母都写磁盘。 |
| **从哪来** | 前端常见性能优化。 |
| **在项目里** | `syncController.ts` 里 `DEBOUNCE_MS = 220`。 |

#### 回声 / 回声过滤

| | |
|---|---|
| **是什么** | A 告诉 B 改文字，B 保存后又告诉 A 同一改动，A 若再改就会**死循环**。过滤 = 认出「这是我自己刚发的」并忽略。 |
| **在项目里** | `DocumentSyncState` 用版本号处理。 |

#### IME / 中文输入法

| | |
|---|---|
| **是什么** | Input Method Editor，打中文时拼音还没选字的那段时间。 |
| **在项目里** | 选字过程中暂不强行刷新整页，否则拼音会乱。 |

## 4. 用白话重讲一遍「03 的结论」

下面**不用上面没解释过的词**。若仍不懂，回到第 3 节查表。

### 4.1 我们有两个产品，各用一款写字工具

| 产品 | 在哪里用 | 用的写字工具 | 为什么 |
|---|---|---|---|
| **MarkdownEditor** | AutoCAD 里弹窗写说明书 | **Vditor** | 团队已用好几年；体验接近 Typora；适合「一整页编辑器」 |
| **HYmd** | VS Code / HYmd Code 里写 `.hy.md` | **Milkdown Crepe** | 要和「文件格式规则」「VS Code 保存方式」「表格块」配合 |

**不是 Vditor 差**，是**两家店厨房设备不同**。

### 4.2 六个理由（极简版）

1. **同一本说明书**  
   HYmd 用 remark 规则读文件；Milkdown 和 remark **同一套圈子**。Vditor 自带 Lute 规则，像**第二本字典**，同一个词两种写法会乱。

2. **VS Code 是老板**  
   文件归 VS Code 存。Milkdown 像**可嵌入的模块**；Vditor 像**整台一体机**，快捷键、颜色主题和 VS Code 容易打架。

3. **表格块要像「贴了标签的附件」**  
   HyMD 要求磁盘上仍能看到 `` ```sheet ... ``` ``。Milkdown 先画出「代码块样子」，再在表面贴表格预览。Vditor 可能把块**揉进正文**，存盘时对不上。

4. **表格别在写字工具里硬做**  
   复杂表格用 **Univer**（专业表格引擎）。Vditor 虽也能做简单表，会和 Univer **做两遍**，维护双倍。

5. **两个仓库各干各的**  
   HYmd 是独立项目，不必把 AutoCAD 那套网页模板原样搬过来。

6. **分工**  
   CAD 里继续用 Vditor；通用 HyMD 文档在 IDE 里用 Milkdown。**共享文件格式**，不共享写字工具。

### 4.3 Vditor 明明功能更多，算不算吃亏？

对 **「单独写技术文章、要公式、要插图」** 来说，Vditor 更强。  
但 HYmd 的目标不是再做一个 Typora，而是：

- 文件必须是**普通 Markdown 加围栏**；
- 大表格在 **Univer**；
- 在 **VS Code** 里编辑。

这些目标下，Vditor 多出来的功能**很多用不上**，反而增加「两套规则、两种保存方式」的风险。所以**不是吃亏，是换赛道**。

### 4.4 一句话

> **在 CAD 里图方便，用 Vditor 写得像 Typora；在 IDE 里守文件格式和表格块，用 Milkdown。**
